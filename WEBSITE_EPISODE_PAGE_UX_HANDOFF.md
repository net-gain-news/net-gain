# Episode page UX: show notes, transcript, and a sticky header

Design-only handoff from a conversation in the pipeline/ops Claude Code project (2026-09-23) — no code was written for any of this, it's mockups and decisions only. For whichever session has the actual WordPress theme/site code, since that project built the site and has the real CSS/JS this needs to be checked against.

## The goal, in one paragraph

The individual episode page's body is currently the full spoken-word transcript (`ng_script_final`, rendered as `post_content` by `class-rest-website-publish.php`). There's real SEO/AEO value in keeping that much text on the page — full transcripts are a well-established practice for podcast SEO, and this show's content is already written to be keyword/entity-rich. But a page whose entire visible body is continuous transcript prose reads like a written news article, which is a real positioning risk for a show that's aggregating/re-narrating news, not producing original reporting. The goal is to keep the SEO value of the full text while making the page *read* like a newscast's show notes by default, not a print article.

## Decision 1: restructure the episode page body

Keep the full transcript on the page (SEO/AEO value preserved — it's real, crawlable, indexable HTML either way), but demote it behind a native, closed-by-default `<details>` disclosure, with the Captivate-style show notes as the primary visible content instead.

Proposed content order (player and pull-quote excerpt stay exactly as they are today):

1. Audio player embed (unchanged)
2. Pull-quote excerpt (unchanged — this is `ng_meta_website_excerpt`)
3. **Show notes** — the Captivate-style per-story paragraphs (`ng_meta_captivate_notes`, or a website-specific equivalent generated the same way — see "Open question" below)
4. **Stories & links** (`ng_story_links`, already a structured field as of the 2026-09-20 split)
5. **Full transcript** — `<details id="transcript"><summary>Full transcript</summary>...(the current post_content transcript text)...</details>`, collapsed by default

No JavaScript needed for the disclosure itself — plain `<details>`/`<summary>`, matching this plugin's existing zero-JS pattern (e.g. the dashboard's test-shows disclosure).

**Open question, not resolved in this conversation**: whether "show notes" on the website reuses `ng_meta_captivate_notes` verbatim, or gets its own dedicated field generated by the same metadata call. Captivate notes are written assuming Captivate's own rich-text editor (real `<p>` tags, `<a rel="nofollow">` links already baked in per the 2026-09-14 fix) — that's probably directly reusable as website body HTML with little or no adaptation, but confirm the HTML renders cleanly in this theme before assuming it's a straight copy.

## Decision 2: the episodes-list "Transcript" button should jump straight to it

Today, every "Transcript" button on `/edtech/episodes/` links to a bare episode URL with no fragment (confirmed live, 2026-09-23 — e.g. `.../idp-education-rejects-blackstone-bid-as-czi-melania-trump-launch-edtech-initiatives/`, nothing after it) — so it's currently just a duplicate link to the same page as the title/thumbnail.

Fix: change those hrefs to append `#transcript`. Modern browsers (current Chrome, Firefox, Safari, Edge) natively auto-scroll to **and auto-open** a `<details>` element when the URL fragment targets it or an element inside it — this is standard HTML platform behavior, not a script. No JS needed here either.

## Decision 3: a sticky header, which fixes two problems at once

**Problem A**: navigating straight to `#transcript` via native fragment scrolling positions that element at the very top of the viewport (`scrollIntoView({block:'start'})`-style behavior) — meaning the hero graphic, headline, player, and show notes all scroll out of view above it. A visitor landing this way has zero context about which show or episode they're on.

**Problem B (reported by the user, separately)**: on mobile - confirmed at least on Safari/macOS - clicking the hamburger menu while scrolled partway down the page never shows the menu entries; they render off-screen.

**Proposed single fix for both**: make the site's *existing* main nav header sticky (`position: sticky; top: 0`) rather than adding a second bar. Once scrolled past the hero on an episode page, show a condensed episode title next to the logo in that same sticky bar, so anyone landing on `#transcript` still has show/episode context.

This plausibly fixes Problem B as a side effect, not a separate patch: if the mobile dropdown is positioned relative to the header itself, and the header is currently in normal document flow (scrolls away), then scrolling down moves the header off-screen — and the dropdown, anchored to that off-screen header, opens where the header currently sits *in the document*, not where the visitor currently is in the viewport. That matches "menu entries draw offscreen" exactly. Making the header sticky means the header - and therefore anything anchored to it - is always at the top of the viewport, so the dropdown should always open in view regardless of scroll position.

**This theory is unconfirmed** - nobody in the source conversation inspected the real CSS/JS behind the mobile menu. Before implementing, actually check: is the dropdown currently positioned relative to the header (supporting the theory above), or is something else going on (a JS bug, a z-index issue, a fixed-height container clipping it)? The mockups built during the conversation used a plain `<details>`/`<summary>` for the hamburger toggle as one clean, zero-JS way to implement it - but that's a suggestion for *if* this gets rebuilt, not a claim about how it works today.

## Related, but not this project's job: YouTube description length

Came up in the same conversation, different codebase (this project's own `pipeline/metadata_generation.py`, not the website): the current `youtube_description` prompt is deliberately dense-and-short with a mandatory keyword-first ~125-character opening. The recommendation there was to make it *more substantial* (more like Captivate notes' per-story depth) while keeping that same front-loaded hook - not to just paste in Captivate notes verbatim, since YouTube's own native "...more" truncation already solves the "don't overwhelm the viewer" problem there, unlike the website. This is flagged here only so it isn't lost - it's a pipeline-side change, not a website one, and hasn't been implemented yet either.

## What to verify before building any of this

- Whether the mobile hamburger menu really is positioned relative to the header (confirms/denies the Problem B theory above).
- Whether `ng_meta_captivate_notes`' HTML renders cleanly as website body content as-is, or needs adaptation.
- Cross-browser/cross-version support for `<details>` auto-open-on-fragment-target if this needs to support older browsers than current evergreen Chrome/Firefox/Safari/Edge.
