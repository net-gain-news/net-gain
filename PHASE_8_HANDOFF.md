# Phase 8 handoff — Image pipeline

For the session with WPVibe/cPanel access, after Phases 1–7 are installed. Needs a real Vertex AI setup (the dedicated GCP project from `CLAUDE.md`'s credentials table, Gemini 2.5 Flash Image reachable on it, a service account JSON) before the Python side of this phase can do anything real — the WordPress side (fallback images, duotone fields, the review UI) is independently testable without it.

## Install — two things beyond the usual plugin swap

1. **Deactivate → delete → upload the new zip (v0.6.0 or whatever the session currently has checked out) → activate**, as always. Deactivating and reactivating matters more than usual this phase: `Net_Gain_Roles::grant_capabilities()` previously only ever ran once, at original plugin activation — a capability added to the code (like this phase's `upload_files` grant to `ng_service`, needed for `POST /wp/v2/media`) would otherwise silently do nothing on an already-installed site. This phase adds a generic fix for that class of problem: `Net_Gain_Roles::maybe_upgrade()` runs on every `init` and re-applies `register_roles()` + `grant_capabilities()` whenever the stored `ng_db_version` option doesn't match the plugin's current `NET_GAIN_VERSION` constant — so a plain reactivation (which bumps nothing on its own) isn't actually what fixes this; the *next page load after the new code is live* is. No manual action needed beyond the normal install, but if `POST /wp/v2/media` ever 403s for the service account, confirm `ng_db_version` (via `wp option get ng_db_version` or similar) actually matches `NET_GAIN_VERSION` before assuming something else is wrong.
2. No Permalinks flush needed this phase — no new rewrite rules.

## The one thing that genuinely needs live confirmation

`image_generation.py`'s `generate_base_image()` calls Gemini 2.5 Flash Image ("Nano Banana") via `client.models.generate_content()` with `response_modalities=["IMAGE"]` and an `image_config=types.ImageConfig(aspect_ratio="16:9")` — a multimodal `generateContent` call, not a dedicated image-generation endpoint, so the response is a list of content parts and the code picks whichever part carries `inline_data`. This is explicitly flagged in that file's own docstring as **not yet verified against a real response** — the model id, the `image_config` field name/shape, and exactly where the inline image bytes land could all be slightly off. The first real run against live Vertex AI credentials is also the first real test of this call shape; if it throws or returns no image data, check the raw `response` object the error message echoes back, against Gemini's current Vertex AI documentation, rather than assuming the pipeline itself is broken.

## Click-through test

1. **Show setup screen** — on an existing show's Edit Show page, confirm three new things appear below the existing branding-frame pickers:
   - **Default fallback images** — three pickers (Podcast art fallback 3000×3000 JPEG, YouTube art fallback 1280×720 JPEG, Website art fallback 1200×630 WebP), same `wp.media` picker UI as the branding frames above them. Upload a real finished image to each (not a frame template — these are the actual pre-rendered images used if AI generation fails) and confirm they save and reappear as thumbnails after a page reload.
   - **Image style** — a collapsed `<details>` disclosure titled "Image style (optional — default: none)". Expand it, switch the dropdown to **Duotone**, and confirm two colour fields appear (Shadow colour, Highlight colour), each a native colour swatch next to a plain hex text input that stay in sync with each other as you change either one. Save, reload, and confirm the disclosure is now **open by default** (since a non-"none" style was saved) and the chosen hex values persisted.
2. **Real image generation end-to-end**: get a real episode to `audio_received` (Phases 3–4). Run `tick.py` by hand and confirm `images_rendered` goes to `in_progress` then `done` — watch for: the independent Claude call that turns the final script into an image prompt (`image_prompt.py`), one Gemini image-generation call, the duotone treatment if this show has one configured, three cover-crop + frame-composite + size-capped-encode passes, three media uploads.
3. Confirm all three resulting images actually look like variations of the **same** underlying art (same subject/composition, just cropped differently) — not three unrelated images. This is the whole point of generating one base image instead of three independent ones.
4. **Graceful fallback path**: temporarily break Vertex AI credentials (wrong project/region/service-account JSON) for a show that already has all three fallback images uploaded (step 1), then re-trigger image generation. Confirm `images_rendered` resolves to **degraded**, not failed, and the episode's `ng_image_square_id`/`ng_image_16x9_id`/`ng_image_1200x630_id` fields end up pointing at the fallback attachment IDs, not empty. Then restore real credentials and confirm a genuine regeneration succeeds and resolves to `done`.
5. **My Show page** (as the assigned talent, or an admin with a talent assignment): once `images_rendered` is `done` or `degraded`, confirm an "Episode images" block appears below the audio/countdown card — three thumbnails (120×120), a "(fallback used...)" note if this run used the fallback path, and a **Regenerate Images** button. Click it and confirm a "Regeneration queued" notice appears and a subsequent `tick.py` run actually re-renders.
6. **Episode Detail page** (admin): confirm the same three image thumbnails (150×150) appear next to the Images status line, alongside the pre-existing Generate/Regenerate Images trigger button.

## Known stubs / deferred (not bugs)

- No exact pixel target for the base image's own generation aspect ratio beyond "widest of the three outputs" (~1.91:1, approximated as Gemini's `"16:9"` preset, the widest preset generally offered) — `cover_resize()` handles the exact final per-output dimensions regardless of this small upstream mismatch, so it's not a correctness issue, just a documented judgment call.
- YouTube publishing (Phase 9) is a separate, later phase — not touched by this one, even though this phase is what makes the YouTube-shaped 16:9 art exist in the first place.
- No UI to preview or adjust the duotone treatment's effect before saving — the two colour fields save blind; the only way to see the result is a real episode's generated images.
